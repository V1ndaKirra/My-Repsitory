# Brainstorm Route

这份文档定义 thesis-writing skill 如何接入 `superpowers brainstorm`。

目标不是把 brainstorm 当成“代写器”，而是把它当成“用户协作分析器”：

- 帮用户回忆系统是怎么一步步开发出来的
- 帮用户拆解真实问题的排查与修复过程
- 帮用户决定还缺哪些截图、代码片段、配置图和运行结果图
- 帮用户把复杂实现讲成答辩时能说清的话

## Core Rule

`superpowers brainstorm` 只能用来：

- 生成分析提纲
- 梳理开发顺序
- 拆解问题排查步骤
- 组织截图和证据清单
- 帮用户把“知道做过但一时说不清”的内容讲清楚

不能用来：

- 编造项目事实
- 代替代码扫描
- 代替用户确认
- 编造截图内容
- 编造论文正文中的实现细节

## When To Invoke

### Chapter 5: System Implementation

优先在这些情况触发：

- 已经知道模块做过，但不知道怎么写成“开发过程”
- 用户提供了代码截图或页面截图，但不会组织叙述
- 一个模块涉及页面、接口、服务、SQL 多层，讲起来容易乱

推荐目标：

- 产出“先做了什么 -> 后做了什么 -> 中间卡在哪里 -> 最后怎么验证”的结构
- 产出“这张截图证明什么，这段代码证明什么”的解释草稿

### Chapter 6: Test And Debug

优先在这些情况触发：

- challenge_log 里已经有候选问题，但缺 symptom / diagnosis / fix / result
- 用户只记得报错，不记得完整排查过程
- 用户知道修过 bug，但说不清为什么这么改

推荐目标：

- 产出“现象 -> 排查 -> 修复 -> 结果”的完整链路
- 明确需要用户补哪些报错截图、修复后截图、运行结果截图

### Screenshot Planning

优先在这些情况触发：

- 需要把“应该补哪些截图”拆成最小可执行清单
- 用户截图很多，但不知道哪些最值得放进论文
- 系统实现章节看起来工作量不够，需要补强证据

推荐目标：

- 给出截图优先级
- 每张截图说明“证明点”
- 建议截图对应哪一章哪一节

## Expected Output Shape

每次 brainstorm 最好围绕一个模块或一个问题，不要一口气分析整篇论文。

推荐输出结构：

```text
1. 这个模块/问题的边界是什么
2. 开发或排查顺序是什么
3. 哪一步最值得写进论文
4. 还缺哪些真实证据
5. 建议补哪几张截图
6. 可以怎样在正文里讲
```

## Safe Usage Pattern

如果环境里有 `superpowers brainstorm`：

1. 先给它真实输入：
   - 模块名
   - 代码路径
   - 接口路径
   - 已知问题现象
   - 已有截图或日志
2. 只让它做结构化分析，不让它补事实
3. 输出后回到 thesis-writing skill 自己核对代码、截图和配置
4. 经过用户确认后，才能把分析结果写进论文或 chapter kits

如果环境里没有 `superpowers brainstorm`：

1. thesis-writing skill 自己按同样结构做普通对话引导
2. 仍然要求用户补真实截图、真实代码、真实问题证据
3. 不要因为缺少这个 skill 就跳过“实现过程复盘”和“问题排查拆解”

## Do Not

- 不要把 brainstorm 的草稿直接当论文正文
- 不要把 brainstorm 推断出来的步骤当成已证实事实
- 不要在用户还没确认时就把 brainstorm 输出写成最终结论
- 不要一次让 brainstorm 处理多个大模块，容易失真
